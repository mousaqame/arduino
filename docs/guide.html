Confirm Windows sees the board before anything else:

Get-CimInstance Win32_PnPEntity |
  Where-Object { $_.Name -match 'COM\d+' } | Select-Object Name, DeviceID

You want Arduino Uno (COM3). A genuine Uno reports VID_2341&PID_0043; CH340-based clones show a different name and work identically. Note the COM number — everything below uses it.

01

The toolchain you already have

Installing Arduino IDE 1.8.x also installs a complete command-line toolchain that most people never touch. There is nothing else to download.

ToolJob
arduino-builder.exeresolves libraries, generates prototypes, drives the compiler
avr-gcc.execompiles
avrdude.exewrites flash over USB
avr-size.exereports flash and RAM usage

The first lives in the install root; the rest in hardware\tools\avr\bin. Three libraries are needed, all from the IDE's Library Manager: Adafruit_SSD1306, Adafruit_GFX_Library, and Adafruit_BusIO — the last arrives automatically as a dependency.

02

The flash script

A wrapper around two commands: arduino-builder to compile, then avrdude to upload. -VerifyOnly stops after compiling, so a broken sketch never reaches a working board. 

# compile
arduino-builder.exe -compile `
  -hardware "<ide>\hardware" -tools "<ide>\tools-builder" `
  -tools "<ide>\hardware\tools\avr" `
  -built-in-libraries "<ide>\libraries" -libraries "<sketchbook>\libraries" `
  "-fqbn=arduino:avr:uno" -build-path <build> <sketch>.ino

# upload
avrdude.exe -C "<ide>\hardware\tools\avr\etc\avrdude.conf" `
  -p atmega328p -c arduino -P COM3 -b 115200 -D `
  -U "flash:w:<build>\<sketch>.ino.hex:i"
PowerShell trap · argument expansion

-fqbn=$Fqbn passes the literal text $Fqbn and the build fails with invalid fqbn. Quote the whole token — "-fqbn=$Fqbn" — so the variable actually expands.

PowerShell trap · stderr redirection

Never pipe a native executable through 2>&1 in PowerShell 5.1. avrdude writes its progress bars to stderr; redirecting wraps each line in an ErrorRecord and reports failure even when the upload returned exit code 0.

03

Firmware: the blocking problem

The original sketch beeped like this:

tone(buzzerPin, 1000);
delay(100);
noTone(buzzerPin);
delay(400);   // nothing else happens for half a second

Fine for a standalone sketch. It breaks the moment serial is added: incoming commands sit unread in a 64-byte buffer while the CPU idles inside delay(), and anything past 64 bytes is silently dropped.

The fix is a state machine on millis(). Rather than waiting, record when the last change happened and check whether enough time has passed: 

void serviceBuzzer(unsigned long now) {
  if (beepFreq == 0) {
    if (beepAudible) { noTone(buzzerPin); beepAudible = false; }
    return;
  }
  if (beepOnMs == 0 && beepOffMs == 0) {          // continuous tone
    if (!beepAudible) { tone(buzzerPin, beepFreq); beepAudible = true; }
    return;
  }
  unsigned int phaseLen = beepAudible ? beepOnMs : beepOffMs;
  if (now - beepPhaseAt >= phaseLen) {            // time to flip
    beepPhaseAt = now;
    beepAudible = !beepAudible;
    if (beepAudible) tone(buzzerPin, beepFreq); else noTone(buzzerPin);
  }
}

The loop then never blocks — each job runs on its own interval:

void loop() {
  unsigned long now = millis();
  serviceSerial();
  if (now - lastMeasure >= MEASURE_MS)   { lastMeasure = now; measure(); applyZone(); }
  serviceBuzzer(now);
  if (now - lastDisplay >= DISPLAY_MS)   { lastDisplay = now; drawDisplay(); }
  if (now - lastTelem   >= TELEMETRY_MS) { lastTelem   = now; sendTelemetry(now); }
}

Two gotchas this build hit

Custom types need their own header

arduino-builder auto-generates function prototypes and injects them right after your #include lines. A function like const char *zoneName(Zone z) gets a prototype above the enum Zone that defines it, and the build fails with 'Zone' was not declared in this scope. Move the enum and struct into a types.h beside the sketch and include it — the prototypes then land after the types are known.

The OLED redraw can starve the loop

A full 128×32 refresh is 512 bytes over I²C. At the default 100 kHz that is roughly 50 ms — half the telemetry budget — and the stream ran at 8 Hz instead of 10. Adding Wire.setClock(400000) after display.begin() measured 9.9 Hz with a median gap of exactly 100 ms. begin() sets its own clock, so calling it earlier does nothing.

04

The serial protocol

Deliberately plain text: newline-terminated, human-readable, debuggable from any serial monitor. No binary framing, no checksums — USB serial is reliable enough at this scale, and being able to type GET into a terminal is worth more than the bytes saved.

Board to PC, streamed at 10 Hz:

T <millis> <distance_cm> <zone>      e.g.  T 12345 42.5 GOOD

999.0 means the sensor got no echo. Replies are OK …, ERR …, or # … for informational lines.

CommandEffect
PINGreplies OK PONG — liveness check
GETdump current configuration
SET <zone> <cm>retune a threshold, 1–400 cm
MODE AUTO|MANUALMANUAL freezes the parking logic's LED and buzzer control
LED ON|OFF|AUTOmanual override; requires MANUAL mode
BUZZ <freq> <ms>one-shot beep, 31–5000 Hz
MUTE ON|OFFsilence the buzzer, keep everything else
SAVEpersist thresholds to EEPROM
RESETrestore defaults; does not auto-save

Zones

FAR > 100 cm
CLOSE > 50
GOOD > 20
V.CLOSE > 10
STOP! ≤ 10

Parsing is strtok plus strcasecmp into a fixed 48-byte buffer — no String objects, which fragment the Uno's 2 KB of RAM. Every literal is wrapped in F() so it stays in flash. Final usage lands at 65% flash and 37% RAM.

Why saving is explicit

Config is a struct guarded by a magic number: read it on boot, and if the magic doesn't match, the EEPROM was never written so load defaults instead. Writing is triggered only by SAVE, never automatically on every SET — EEPROM endures roughly 100,000 writes, and live-tuning with a slider would burn through that quickly. 

EEPROM.get(EEPROM_ADDR, cfg);
if (cfg.magic != EEPROM_MAGIC) loadDefaults();
05

The PC dashboard

Two files. Python owns the serial port and serves; the browser renders. 

browser  <--SSE--->  dashboard.py  <--serial-->  Arduino
         <--POST-->

A web page cannot open a COM port, so something native has to hold the connection. A small Python process sits in the middle: it reads telemetry, fans it out to browser clients over Server-Sent Events, and relays commands back via POST /cmd. SSE rather than WebSockets because the data flows almost entirely one way and SSE needs no dependencies — http.server plus a text/event-stream response is enough. The only third-party package in the whole project is pyserial.

What matters in the bridge

Opening the port reboots the board. The USB-serial chip toggles DTR on connect, and setup() then holds its splash for two seconds. Sleep about three seconds after opening before expecting sane data.

Never let a slow client stall the reader. Each browser gets a bounded queue; if it fills, drop frames rather than block the serial thread. 

try:
    q.put_nowait(event)
except queue.Full:
    pass   # slow client — drop rather than stall

Buffer history server-side so a browser opening late gets a populated chart instead of an empty one. A deque(maxlen=240) holds about 24 seconds at 10 Hz.

What matters in the UI

Repaint on requestAnimationFrame, not per message. At 10 Hz it barely matters, but decoupling render rate from data rate means a faster board can never out-run the renderer.

Median-filter the headline number. HC-SR04 sensors throw occasional wild readings — consecutive samples during testing measured 338, 342, 44, 341 cm. A median of the last three kills the flicker without hiding anything: the chart still plots raw, and the exact raw value stays visible in the subtitle.

Don't clobber an input the user is typing in. Config updates arrive continuously, so track which field has focus and skip it on refresh.

No echo is not zero centimetres

An early version pinned the proximity marker to the far-left of the bar on a no-echo reading — the red STOP end — implying something was touching the sensor when in fact nothing was in range. Hide the marker instead of placing it at zero. Sensor absence and sensor danger must never render alike.

06

Running it

python dashboard.py          # then open http://127.0.0.1:8787
The one thing everyone trips over

Only one process can hold a serial port. Stop the dashboard before flashing, or avrdude fails with access denied.

Order of operations when changing firmware:

  1. Stop the dashboard with Ctrl-C.
  2. Compile alone: flash.ps1 -Sketch parking_serial -VerifyOnly
  3. Upload: flash.ps1 -Sketch parking_serial
  4. Start the dashboard again.

08

Rebuilding from scratch

  1. Install Arduino IDE 1.8.x — it supplies the entire toolchain.
  2. Library Manager → install Adafruit SSD1306, accepting the GFX and BusIO dependencies.
  3. Install Python 3, then pip install pyserial.
  4. Copy the project folder anywhere.
  5. Wire per section 00, confirm the COM port, and adjust -Port if it isn't COM3.
  6. Flash parking_serial, then run dashboard.py.
PathRole
parking_serial/firmware currently on the board
parking_serial/types.henum and config struct, split out for prototype ordering
parking_sensor/original sketch, untouched — the restore point
flash.ps1compile and upload
dashboard.pyserial bridge and web server
dashboard.htmldashboard UI
.build/compiler output — safe to delete

The original sketch is preserved untouched, so flashing parking_sensor returns the board to exactly its prior state at any time.
